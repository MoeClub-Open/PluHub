# PluHub 开发理念与架构原则

**文档版本：** v0.2（讨论稿）  
**编写日期：** 2026-10-18  
**项目名称：** PluHub（独立项目品牌，正式发布前核验名称与商标）
**GitHub 托管组织：** [MoeClub-Open](https://github.com/MoeClub-Open)（公司开源组织）  
**项目定位：** A composable, high-performance, plugin-driven gateway platform.  
**一句话主张：** **网关是一组可组合能力，而不是一套不可拆分的业务系统。**

> 本文是 PluHub 的工程理念与设计约束，用于统一开发方向、评审架构取舍、指导仓库划分和插件接口演进。它不是最终 API 规范、性能承诺，也不是对具体技术选型的永久冻结。详细协议、数据结构和组件 API 应在后续独立设计文档中明确。

## 01｜愿景与定位

PluHub 希望提供一个**高性能、开放、可扩展的通用网关平台**。开发者能够按需组合 HTTP 反向代理、AI 协议转换、模型路由、账号池、鉴权、限流、限速、用量统计、计费、支付、日志及管理界面，而不必购买或部署一套包含所有功能的单体系统。AI Gateway 是首个重点场景，但产品定位不被 AI 或特定上游 API 限定，未来可以扩展到普通 HTTP 服务、WebSocket、MCP 和其他协议场景。

项目面向个人自托管用户、团队内部平台和需要商业化能力的 API 服务提供者。三类用户应尽量共享同一套核心和插件协议：轻量用户只安装必要组件，内部用户组合路由、身份与治理能力，商业用户在此前基础上安装可靠的用量与财务服务。**复杂度由已选择的能力产生，而不是由框架默认强加。**

成功的标准不是“内置功能最多”，而是新能力可以独立开发、测试、发布、替换和停用；性能成本可测量，失败边界可理解，第三方开发者不必阅读整个主系统源码即可编写插件。

## 02｜需要长期坚持的开发理念

### P01　一切业务能力皆插件，但内核必须真实可靠

反向代理、协议转换、限流、计费、日志、支付以及前端管理页面均通过插件对外提供。内核本身不应写死 AI Provider、账单模型或支付方式。但“一切皆插件”不意味着内核是空壳：插件发现、生命周期、依赖解析、权限执行、配置装配、能力注册、执行图切换和宿主信任边界属于不可缺少的基础设施。系统必须先拥有稳定的宿主契约，才能谈业务能力的自由组合。

### P02　插件是交付单位，能力是组合单位，运行时是执行单位

**Plugin** 表示安装、更新、权限申请和生命周期的单位；**Capability** 表示插件对外提供的标准服务，如 `routing.selector@1`；**Runtime** 表示实际执行方式，包括进程内 TypeScript 和独立进程；**Pipeline** 则决定能力在一次请求中的执行关系。四者不能混为一谈。一个插件可以提供多个能力，同一种能力可以由多个插件实现，且相同插件包既可以包含后端，也可以包含前端资源。

### P03　默认模块化，不默认微服务化

模块边界应从第一版明确，但模块化不等于每个模块都需要自己的进程、数据库和消息队列。单节点应支持仅用 Node.js 加本地存储运行；在业务规模、隔离或性能要求出现后，再把适合的能力升级为 Sidecar、独立服务或集群部署。部署边界由实际压力与可靠性要求决定，不由仓库目录决定。

### P04　TypeScript 主系统，语言无关的插件协议

主程序、插件微内核、控制面和管理前端采用 TypeScript 作为主要开发语言。正式支持 TypeScript 和 Go 插件；其他语言可依据公开的进程通信契约接入，官方 SDK 再按社区需求增加。 **不要求使用 Rust，也不为 Rust 工具链增加项目基础依赖。** 公开插件协议不能泄露 Node.js 框架、内部依赖注入容器或某个第三方 RPC 框架的实现细节。

### P05　稳定的契约优先于稳定的内部实现

插件 API、Capability、Manifest、事件模型和流式处理语义必须有版本策略。主系统内部可以重构，但已发布的公共契约不能随意破坏。应采用显式版本、兼容性测试和过渡适配层；破坏性变化要有迁移方案和明确的废弃周期。插件不应直接导入其他插件的私有源码或访问其他插件的数据库表。

### P06　性能从数据通路设计开始，而不是事后优化

请求级决策与流式字节处理应分离。鉴权、路由、配额检查可以做少量 RPC；高频 SSE Chunk 不应在多个插件进程之间来回序列化。系统至少应支持原样透传、进程内流变换、独立执行器整流处理三种路径，并根据启用的功能选择最短可行路径。只有真实性能基准能够证明何时值得使用 Go Sidecar。

### P07　流式语义是一等公民

HTTP Streaming、SSE、WebSocket、客户端中断、上游取消、背压、超时和半途失败都属于核心执行语义，不是插件自己随意补丁处理的边缘情况。任何会改变响应体的插件必须声明是否需要解析、缓存或改写数据；不需要转换时应尽可能保持原始流。对已经开始向客户端输出的模型响应，默认不进行无语义保障的跨上游拼接与重试。

### P08　依赖图与请求执行图分离

依赖图回答“插件能否启动”，执行图回答“请求怎样运行”。请求处理应使用具名阶段，例如 Ingress、Identity、Planning、Admission、Execution、Streaming、Finalize，而非靠各插件随意声明一个数字优先级来形成脆弱的隐式顺序。配置变更后先静态校验，再生成不可变执行图；每个进行中的请求固定使用启动时对应的图版本。

### P09　商业功能可选，账务正确性不可选

Metering、Pricing、Billing、Wallet、Subscription、Payment 是不同能力，并应可以分别安装。纯反代不依赖计费，只有用量统计的内部网关不依赖支付；一旦启用资金相关功能，则必须满足幂等、持久化、可审计、可恢复与对账的要求。普通日志可以按策略异步采样，余额扣减和支付入账不能依赖可能丢失的普通广播事件。

### P10　前后端一体插件，但信任级别分层

插件可以同时提供后端服务、管理 API、路由页面、菜单入口、配置 Schema 和组件插槽。前后端由同一个 Manifest 和版本管理，但运行在不同宿主环境。官方可信前端扩展可通过受控动态模块加载；不可信第三方 UI 应采取隔离 iframe 和受限的 Host API。插件包格式统一不代表所有插件自动获得同等权限。

### P11　安全边界不可只停留在声明

每个插件必须声明其需要的能力和权限，宿主必须在运行时执行相应访问控制。外部进程默认不等于沙箱，需要操作系统权限、进程资源、文件与网络访问约束。插件签名、包完整性、依赖来源、SSRF 防护、密钥引用、敏感日志脱敏和升级回滚都应进入架构设计。宿主的签名校验、权限根和安全审计不能被普通插件随意取代。

### P12　默认轻量、运维可见、性能可测

优先保证简单场景的安装体验：纯反代不应被迫部署 PostgreSQL、Redis、NATS 或大型控制平台；复杂功能需要这些依赖时，通过 Capability 声明并清晰提示。内核应提供可观测性接口、可复现的配置、性能基准和故障注入测试。任何“高性能”宣传必须附带测试环境和对比基线，而不是只给出理论吞吐量。

## 03｜明确的架构边界

| 层次 | 负责什么 | 明确不负责什么 |
| --- | --- | --- |
| **Kernel** | 注册、依赖、生命周期、权限、配置、能力发现 | 业务路由规则、支付和模型定价 |
| **Gateway Engine** | 请求上下文、阶段执行、流生命周期、取消与排空 | 固定某一种协议转换算法 |
| **Plugin Runtime** | TS Native、独立进程、RPC/数据流桥接 | 定义具体业务能力的含义 |
| **Control Plane** | 安装与升级、配置版本、集群分发、管理 API | 直接逐 Token 操作请求体 |
| **Frontend Host** | 页面/菜单/组件插槽、资源加载、权限检查 | 将第三方 UI 默认视为可信 |
| **Contracts & SDK** | 插件协议、Capability、Manifest、测试工具 | 依赖主系统内部源代码 |
| **Business Plugins** | 反代、AI、限流、计费、支付、日志等 | 绕过宿主契约访问其他插件内部状态 |

控制面与数据面**逻辑分离**，但第一版允许同进程部署。插件可以本地调用、跨进程调用或远程调用，但公开 Capability 的业务语义应尽量一致。系统不能为了“看起来更模块化”而人为制造多个不必要的网络跳点。

### 三种执行路径

1. **Raw Pass-through：** 只做必要准入和路由，直接透传 HTTP/SSE/WS，尽量不反序列化响应内容。
2. **Native Transform：** 在 TypeScript 进程中执行受信任的解析和变换，适合大多数 AI 协议转换。
3. **Sidecar Stream：** 将一整段代理或转换任务交给 Go 等独立插件进程处理；控制信息可用 RPC，数据流通过长连接/本地 Socket 连续传输。

性能优化原则是**减少数据复制和跨进程边界**，而不是让插件实现语言决定性能。针对请求级钩子、Chunk 级变换和独立流处理分别建立基准测试。

## 04｜一个插件的完整定义

正式的全栈插件包至少可以包含：`manifest`、后端代码或二进制、可选前端 Bundle、配置 Schema、可选数据迁移及完整性信息。Manifest 描述插件 ID、版本、宿主兼容范围、所提供与依赖的 Capability、运行方式、权限、配置、UI 扩展点和适用平台。它是插件发现与部署的依据，不是任意代码执行入口。

插件生命周期建议采用 **Discovered → Validated → Installed → Resolved → Starting → Ready → Active → Draining → Stopped**；失败状态与回滚路径单独处理。新版插件健康检查和兼容性验证完成后，才允许接管新请求；旧版实例排空已有 SSE/WS 连接后再释放。进程内 ESM 插件的注册可以撤销，但不应承诺所有 JS 模块都会从运行时内存中被彻底卸载。

正式接口至少分为三类：**Capability（能力服务）**、**Pipeline Hook（执行拦截）**和**Event（事件订阅）**。Capability 用于可替换实现，Hook 负责明确阶段中的同步决策和变换，Event 用于异步通知；关系到资金、凭证或其他持久业务事实的事件必须有可靠交付与恢复机制。

插件作者应获得稳定的 TypeScript SDK、Go SDK、Manifest 校验器、模拟 Host、流式测试工具和本地开发热重载支持。不能让开发者为了做一个限流插件而先理解整个主程序的内部架构。

## 05｜网关能力的可组合方式

| 运行形态 | 所需能力组合 | 不应强制依赖 |
| --- | --- | --- |
| **Minimal Proxy** | Listener + Raw Proxy + Transport | AI Codec、钱包、支付、外部数据库 |
| **AI Gateway** | Listener + Codec + Provider + Router + Transport | 充值、订阅、前端商业功能 |
| **Internal Gateway** | AI Gateway + Auth + Limiter + Metering + Observability | Payment、Wallet |
| **Commercial Gateway** | Internal + Pricing + Wallet + Billing + Payment/Subscription | 某一种固定支付平台或存储驱动 |

这四个示例不是四份源代码，而是由同一套 Kernel 加不同的 Profile 装配出来的系统。允许依赖自动校验，但不能把一个 Profile 中的全部组件绑定成不可拆分的安装包。

**费用处理示例：** 先获得价格版本与预估值，执行额度预留，再完成上游调用，保存真实或标记为估算的用量，进行幂等结算与补偿对账。支付插件只提供可信支付结果，钱包插件维护账本，计费插件完成结算策略。客户端断连不等于上游没有产生费用，因此需要 `Pending Reconciliation` 等可恢复状态。

## 06｜高性能与可靠性的共同约束

性能不是单一 RPS 数值，而是给定功能组合下的额外 p50/p95/p99 延迟、TTFT 开销、吞吐量、连接规模、内存占用和失败恢复能力。必须对纯直连、TypeScript 原样反代、Native Codec、Go Sidecar 处理建立同环境基准；只有当 Go 替代实现证明有实际收益时才引入它。初期不对外承诺未经验证的极限并发或固定 TTFT 数值。

每个流式请求必须保证有界缓冲、端到端背压、统一超时/取消信号和资源释放；每次重试必须明确是否已经向客户端发送内容、是否可能产生上游费用、是否执行过不可逆动作。限流插件的 RPM、TPM、并发、队列、输出 TPS 属于不同的资源政策，不应简单合并为一个黑盒。输出 TPS 控制的是下游发送速度，不等于限制上游模型实际生成速度。

可靠性上，应定义“普通诊断可采样，财务事实不可无声丢失”的原则。多节点部署时，关键额度和租约操作需要原子性；计费账本需要幂等键、价格版本、请求/尝试 ID 和恢复任务。插件故障不能导致整个宿主失去控制能力，插件升级不能无条件中断已建立的长连接。

## 07｜代码仓库与发布原则

首期采用**四个仓库**，统一托管于 **[MoeClub-Open](https://github.com/MoeClub-Open)**。主系统采用 Monorepo，各公开包与插件独立发布。**PluHub 是项目品牌，MoeClub-Open 是 GitHub 托管组织；以下仓库名为规划路径，尚未确认创建。**

| Repo（暂定） | 主要内容 | 发布边界 |
| --- | --- | --- |
| `MoeClub-Open/PluHub` | Kernel、Engine、Runtime、Control、Console、CLI、TS SDK、测试工具 | 主程序与 npm 包 |
| `MoeClub-Open/PluHub-Spec` | Protobuf/WIT（按需）、Manifest Schema、Capability/事件/流协议 | 稳定协议版本 |
| `MoeClub-Open/PluHub-SDK-Go` | Go 插件 SDK、RPC 适配、流接口、测试样例 | Go Module |
| `MoeClub-Open/PluHub-Plugins` | 官方网络、AI、策略、商务、可观测性插件 | 每个插件独立版本与安装包 |

仓库托管组织不自动决定代码版权或知识产权归属；贡献授权与维护权限应另外记录。

核心仓库不反向依赖官方插件的私有源码。TS SDK 初期与主系统同仓，使用独立 npm 包版本发布；Go SDK 单独维护。随着生态发展，再考虑独立的 Examples、Documentation Site 和 Registry 仓库，但不提前创建大量空仓库。

推荐的职责方向是：**Spec 定义契约 → Host/SDK 实现契约 → Plugins 使用契约提供能力 → Profiles 选择能力组合。** Git Repo 边界、运行进程边界和插件生命周期边界独立演进，避免为了组织结构牺牲运行效率。

## 08｜开发流程与架构治理

重大架构变动须有轻量 **ADR（Architecture Decision Record）**：记录背景、备选方案、已选方案、被放弃的方案、兼容性影响及未来撤销条件。涉及公开 Capability、Manifest、RPC 协议、计费事实模型或前端扩展 API 的变更，应先经过 RFC 和兼容性测试，再进入实现。代码评审须同时回答“是否新增了不必要的核心依赖”和“能否通过插件单独替换”。

CI 至少覆盖格式与静态检查、插件 Manifest Schema、公共协议破坏性变更检查、Native/Sidecar 合约测试、HTTP/SSE/WS 流式测试、插件故障与排空测试、计费幂等测试以及性能回归。发布必须记录测试环境与基准；性能回归不能只靠肉眼感受。安全审计需要涵盖密钥权限、插件供应链、敏感日志、SSRF 与不可信 UI。

**不做的事：** 不将商业计费绑定进核心；不为了形式上的微服务而要求 Redis/NATS 等全家桶；不把 Rust 当作基础开发门槛；不支持任意不可信脚本获得进程内特权；不追求对所有 AI Provider 的“无损通用格式”幻觉；不将插件 API 长期稳定性建立在尚未稳定的第三方框架之上。

## 09｜阶段计划与完成定义

| 阶段 | 核心成果 | 可验收的完成标准 |
| --- | --- | --- |
| **M0 基础契约** | Manifest v1、Capability v1、Kernel、Native TS/进程运行时、CLI 雏形 | Go/TS 示例插件可安装、调用、停止，权限与依赖校验有效 |
| **M1 数据面** | Listener、Raw Proxy、Undici Transport、编译式 Pipeline | HTTP/SSE/WS 透传正确，取消与背压正常，有首份性能基线 |
| **M2 全栈扩展** | 前端 Extension Registry、UI SDK、Sidecar 流桥接 | 一个 Go 后端 + React 前端插件可安装、升级、卸载并排空 |
| **M3 AI 能力** | Provider、OpenAI/Anthropic/Gemini Codec、Router、Account Pool、Limiter | 多协议、工具调用、流式用量和受控故障转移通过测试 |
| **M4 商业能力** | Metering、Pricing、Wallet、Billing、Payment | 重复事件不重复扣费，断流可对账，账务可恢复 |
| **M5 规模化** | 多节点配置分发、发布签名、回滚、Registry | 滚动更新不破坏既有连接，多个节点保持配置收敛 |

阶段顺序允许根据现实需求调整，但**M0 的稳定插件契约和 M1 的真实数据面基准不可跳过**。第一份能对外演示的产品应该是安装两个插件即可工作的 HTTP 反代，而不是预先实现全部商业后台。

## 10｜已确定的方向与待决策事项

**现阶段的建议性共识：** 主系统与插件宿主优先 TypeScript/Node.js；业务功能以插件接入；插件同时可包含前后端；TypeScript/Go 是第一批开发语言；Go 是可选执行器而非必需内核；Kernel 与业务插件分离；流式性能和账务正确性是不可降低的底线；PluHub 是当前选定的项目品牌名称（商标可用性仍待核验），GitHub 托管组织确定为 MoeClub-Open。

**仍需专项设计评审：** 品牌与商标核验、许可证及贡献者协议；插件签名与分发信任模型；前端 React 扩展接口及 iframe 限制；Sidecar 控制 RPC 与流式数据通道的具体线协议；多实例运行时布局；SQLite/PostgreSQL 数据模型与迁移；权限体系；Token 估算与上游 Usage 冲突处理；插件版本兼容与弃用周期。这些问题应形成独立 ADR，不宜在理念文档里伪装成已验证事实。

## 项目宣言

> **PluHub 不规定网关必须拥有哪些业务能力，它规定这些能力如何安全、高效、可预测地组合。**
>
> **我们以稳定契约保护开发者，以轻量默认保护部署者，以真实基准保护性能，以明确边界保护系统可靠性。**
>
> **一个插件可以改变能力，但不应迫使整个系统改变结构。**
