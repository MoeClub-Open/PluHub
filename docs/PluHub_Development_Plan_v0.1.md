## 00 文档说明

### 0.1 与理念文档的关系

| 维度 | 理念文档 v0.2 | 本开发计划 v0.1 |
| --- | --- | --- |
| 回答的问题 | 为什么这样设计、边界在哪里 | 具体建什么、依赖顺序、何时算完成 |
| 稳定性 | 长期稳定，改动需 ADR | 随里程碑迭代，结构性改动需 ADR |
| 粒度 | 原则（P01–P12）与层次划分 | 工作包（WP）、验收标准、测试与 CI |
| 变更冲突 | 两者冲突时**以理念文档为准** | 冲突必须通过 ADR 明确修订其中一方，不允许静默偏离 |

本计划中的每个工作包都要能回溯到至少一条原则（见附录 A 的追踪矩阵），无法回溯的工作包应被质疑其必要性。

### 0.2 术语约定

| 术语 | 含义 |
| --- | --- |
| Plugin | 安装、升级、权限申请与生命周期的单位，由 Manifest 描述 |
| Capability | 插件对外提供的、可被替换的标准化服务，如 `proxy.raw@1` |
| Runtime | 插件的实际执行方式：`native`（进程内 TS）、`process`（独立进程）、`sidecar`（独立进程 + 流式数据通道） |
| Pipeline | 一次请求中能力的执行关系，由执行图表达 |
| Hook | 在具名阶段中执行同步决策或变换的扩展点 |
| Event | 异步通知扩展点，分诊断、业务事实、财务事实三层 |
| Profile | 一组能力组合与默认配置，用于装配不同形态的网关 |
| Dependency Graph | 回答“插件能否启动”的图，含能力依赖与版本约束 |
| Execution Graph | 回答“请求怎样运行”的不可变执行图，每次配置变更后重新编译 |
| Host | 宿主，指运行插件并提供 Host API 的主系统 |
| Spec | 契约仓 `PluHub-Spec` 定义的 Schema、类型与一致性用例 |
| WP | Work Package，工作包，本文可执行的最小交付单元 |
| DoD | Definition of Done，完成定义，逐条可验证 |
| Gate | 里程碑出口门槛，未全绿不得进入下一里程碑的业务范围 |

### 0.3 本文如何被执行

1. **一 WP 一 Issue**：标题格式 `[M0-WP04] Kernel 生命周期与依赖解析`，标签 `wp:M0-WP04`，挂到对应 Milestone。
2. **一 WP 一 PR（或一组同标签小 PR）**：合并即勾选 Issue，不允许“代码已合并、验收未定义”。
3. **DoD 即验收**：评审时逐条对照 WP 表中的 DoD，不接受“基本可用”这类判断。
4. **里程碑关闭条件**：出口门槛（第 08 章）全部通过，且演示脚本可被任意维护者在干净环境重放。
5. **计划本身可被挑战**：任何 WP 若在实现中证明不可行，先提 ADR，再调整本文，不做无声变更。

### 0.4 关于排期

本文**不排期**。原因如下：

- 依赖顺序比日期更能约束工程质量，而日期会诱导跳过验收；
- 项目当前由少量维护者推进，任何日历承诺都会失真；
- 里程碑之间的墙钟时间应由实际执行方在持有资源信息后换算，本文只提供依赖图与关键路径（见 8.6）。

如果需要排期，正确做法是：先按第 08 章拆 Issue，用历史吞吐量估算，再回填到你们自己的排期工具，**不要写进本文档**。

## 01 目标与成功标准

### 1.1 用户与场景

| 用户类型 | 最小安装 | 需要的能力 | 明确不需要 |
| --- | --- | --- | --- |
| 个人自托管 | 两个插件（Listener + Raw Proxy） | 反代、简单鉴权、日志 | 外部数据库、钱包、支付 |
| 团队内部平台 | Internal Gateway Profile | 路由、身份、限流、用量、可观测性 | 支付、订阅 |
| 商业 API 提供者 | Commercial Gateway Profile | 上述全部 + 定价、钱包、账单、支付 | 某一固定支付平台或存储驱动 |

三类用户共享同一 Kernel、同一插件协议与同一套 Capability。差别只在**装配了哪些插件**，而不是维护三份代码（理念 P03、§05）。

### 1.2 首个可演示产品（DEMO-1）

> 第一份能对外演示的产品，是**安装两个插件即可工作的 HTTP 反代**，不是预先实现全部商业后台（理念 §09）。

DEMO-1 的验收脚本（必须可重放，不依赖演示者记忆）：

1. 在干净目录执行 `pluhub init`，生成最小配置与插件目录。
2. 安装 `official.listener` 与 `official.raw-proxy` 两个插件（本地路径或目录源）。
3. 配置一个上游地址，`pluhub start` 启动。
4. 用 `curl` 验证普通 GET、POST 请求体、chunked 响应、SSE 流均正确透传。
5. 中途中断客户端连接，确认上游连接被释放、无资源泄漏、日志记录取消原因。
6. `pluhub stop`（或 Ctrl+C）后进程退出码为 0，且排空期间不接收新请求。

DEMO-1 明确**不包含**：AI 协议转换、账号池、计量计费、管理界面、外部数据库、集群部署。

### 1.3 工程成功标准

| 编号 | 标准 | 可验证方式 |
| --- | --- | --- |
| S1 | 新能力可独立开发、测试、发布、替换和停用 | 新增一个示例插件不改动内核代码；替换同能力实现只改配置不改代码；停用后执行图重新编译成功 |
| S2 | 性能成本可测量 | `pluhub bench` 在同一环境产出纯直连、TS 反代、Native Codec、Go Sidecar 四路径对照数据 |
| S3 | 失败边界可理解 | 错误模型统一（6.6）；故障注入矩阵（9.6）覆盖插件崩溃、超时、半途失败，并有对应诊断字段 |
| S4 | 第三方开发者不必阅读主系统源码 | 仅凭 Spec + SDK + 示例插件 + 模拟 Host 即可完成一个插件并通过一致性测试 |
| S5 | 默认轻量 | Minimal Proxy Profile 不依赖 PostgreSQL、Redis、NATS 或任何外部服务 |
| S6 | 公共契约可演进 | CI 中的契约破坏性检查生效，破坏性变更必须携带版本与迁移说明（6.9、10.1） |

### 1.4 质量属性目标（方向性，非承诺）

| 属性 | 目标方向 | 度量方式 | 明确不承诺 |
| --- | --- | --- | --- |
| 额外延迟 | Raw Pass-through 路径尽可能接近直连 | 同环境 p50/p95/p99 对照 | 初期不给具体毫秒数 |
| TTFT 开销 | 流式首字节延迟开销可测且稳定 | 首字节时间分布 | 不给固定 TTFT 数值 |
| 吞吐 | 在给定功能组合下可测量、可复现 | RPS × 响应体大小矩阵 | 不给理论极限值 |
| 连接规模 | 长连接可稳定驻留与排空 | 并发连接数与 RSS | 不给固定并发上限 |
| 失败恢复 | 插件故障不导致宿主失控 | 故障注入后的可用性与恢复时间 | 不承诺零中断 |
| 账务正确性 | 重复事件不重复扣费，断流可对账 | 幂等测试与对账测试 | 不承诺“绝不丢事件”，只承诺可恢复 |

对外材料引用性能数字时，必须同时给出测试环境、配置、负载模型与提交版本（理念 P12）。

## 02 范围与非目标

### 2.1 范围内（里程碑摘要）

| 里程碑 | 主题 | 核心成果 |
| --- | --- | --- |
| M0 | 基础契约 | Manifest v1、Capability v1、Kernel、Native/Process 运行时、CLI 雏形、TS/Go 示例插件 |
| M1 | 数据面 | Listener、Raw Proxy、undici Transport、编译式 Pipeline、HTTP/SSE/WS 透传、首份性能基线 |
| M2 | 全栈扩展 | 前端 Extension Registry、UI SDK、Sidecar 流桥接、控制台骨架、安装/升级/卸载闭环 |
| M3 | AI 能力 | Provider、OpenAI/Anthropic/Gemini Codec、Router、Account Pool、Limiter、流式用量 |
| M4 | 商业能力 | Metering、Pricing、Wallet、Billing、Payment/Subscription、对账与恢复 |
| M5 | 规模化 | 多节点配置分发、发布签名、Registry、滚动更新、规模化基准 |

### 2.2 非目标（本期明确不做）

**继承自理念文档 §08 的“不做的事”：**

1. 不将商业计费绑定进核心；
2. 不为了形式上的微服务而要求 Redis/NATS 等全家桶；
3. 不把 Rust 当作基础开发门槛，不为 Rust 工具链增加项目基础依赖；
4. 不支持任意不可信脚本获得进程内特权；
5. 不追求对所有 AI Provider 的“无损通用格式”幻觉；
6. 不将插件 API 长期稳定性建立在尚未稳定的第三方框架之上。

**本计划补充的工程非目标：**

| 编号 | 非目标 | 说明 |
| --- | --- | --- |
| N1 | 首期不做多节点集群 | 多节点属 M5；M0–M4 假设单节点，但不得写死单机假设（存储、配置版本要留接口） |
| N2 | 首期不做插件 Registry 与签名 | 属 M5；M0 仅在 Manifest 预留完整性字段 |
| N3 | 首期不建 `PluHub-SDK-Go` 与 `PluHub-Plugins` 仓 | 采用“主仓 + Spec 两仓”；Go SDK 与官方插件仓按触发条件再拆（4.1） |
| N4 | 不做 Kubernetes Operator、Helm Chart | 部署编排不在本计划范围 |
| N5 | 不追求与某商业网关的功能对齐 | 能力取舍以“可组合性”为准，不以竞品清单为准 |
| N6 | 不提供多租户 SaaS 计费后台 | 计费面向自托管与内部平台，不做运营级多租户控制台 |
| N7 | 不内置业务插件 | `examples/` 只放演示与测试用插件，官方业务插件不进核心仓 |

### 2.3 前置条件与当前事实

| 编号 | 事项 | 当前事实（已核验） | 影响 |
| --- | --- | --- | --- |
| P1 | 主仓 | `MoeClub-Open/PluHub` 已存在，仅有初始提交：`LICENSE`（Apache-2.0）、空 `README.md`、`.gitattributes` | 需补工程基线（M0-WP01） |
| P2 | Spec 仓 | `MoeClub-Open/PluHub-Spec` **尚未创建**（`git ls-remote` 返回 Repository not found） | 属维护者前置动作；未创建前 M0-WP02 只能在本仓草拟 |
| P3 | npm scope | `@pluhub/*` 的可用性**未核验** | 若不可用需改包名，影响面在 4.4，越早核验越好 |
| P4 | 工具链 | 本机 Node v24.11.1、pnpm v10.20.0、Go 1.27.0、git 2.56.0 | 版本下限见 5.10 |
| P5 | CI 环境 | GitHub Actions（Linux runner 为主，Windows job 为辅） | M0 起即需要 Windows 兼容性检查（开发者主力为 Windows） |
| P6 | 商标与许可证 | PluHub 商标可用性未核验；贡献者协议未定 | 不阻塞开发，阻塞**公开发布**（ADR-0010） |
| P7 | 维护者 | 以少量维护者为主 | 自动化与模板优先，人工评审不可作为唯一质量闸门 |

### 2.4 约束

- **许可证**：主仓沿用 Apache-2.0；Spec 仓建议同许可证，最终由 ADR-0010 决定。
- **跨平台**：开发环境（Windows）与 CI/生产（Linux）必须同时可用；文件路径、管道、信号、终端行为差异必须在 M0 就处理。
- **零强制外部依赖**：默认安装路径不得要求数据库、消息队列、容器运行时。
- **语言**：主系统与插件宿主以 TypeScript 为主；Go 仅作为可选执行器与 SDK（理念 P04）。

## 03 架构落地

### 3.1 层次到包的映射

| 理念文档层次（§03） | 落地包/目录 | 负责 | 明确不负责 | 首个里程碑 |
| --- | --- | --- | --- | --- |
| Kernel | `packages/kernel` | 注册、依赖解析、生命周期、权限执行、配置装配、能力发现、执行图编译 | 业务路由规则、计费与定价 | M0 |
| Gateway Engine | `packages/engine` | 请求上下文、阶段执行、流生命周期、取消与排空 | 规定某一种协议转换算法 | M0（骨架）/M1（完整） |
| Plugin Runtime | `packages/runtime` | Native TS 加载、独立进程宿主、RPC 与数据流桥接 | 定义具体业务能力语义 | M0（native + process v0）/M2（sidecar） |
| Control Plane | `packages/control` | 安装卸载、配置版本、图切换、管理 API | 逐 token 操作请求体 | M0（本地）/M2（API） |
| Frontend Host | `apps/console` + `packages/ui-sdk` | 页面/菜单/组件插槽、资源加载、权限检查 | 默认信任第三方 UI | M2 |
| Contracts & SDK | `PluHub-Spec`（仓外）+ `packages/sdk` | 插件协议、Capability、Manifest、测试工具 | 依赖主系统内部源码 | M0 |
| Business Plugins | `examples/plugins/*`，后续 `PluHub-Plugins` | 反代、AI、限流、计费、支付、日志 | 绕过宿主契约访问其他插件内部状态 | M1 起 |

> 说明：`packages/engine` 在 M0 只提供阶段枚举、上下文与执行器接口，真实流处理在 M1 落地；这是为了让 M0 的插件协议能先跑通，不被数据面实现绑死。

### 3.2 三种执行路径与选择规则

| 路径 | 触发条件 | 数据流 | 何时不得使用 | 首个可用版本 |
| --- | --- | --- | --- | --- |
| Raw Pass-through | 执行图中无需要解析响应体的 Hook | 客户端 ↔ 宿主 ↔ 上游，字节双向直通 | 有插件要求改写响应体 | M1 |
| Native Transform | 存在需解析响应体的 Hook，且其 Runtime 为 `native` | 客户端 ↔ 宿主（TS 解析/变换）↔ 上游 | 插件未声明可安全解析，或解析成本未经基准验证 | M1（框架）/M3（AI Codec） |
| Sidecar Stream | 存在声明 `sidecar` 运行的流处理插件 | 客户端 ↔ 宿主 ↔ 独立进程（长连接/本地 Socket）↔ 上游 | 仅做请求级决策的插件；无基准证明收益的场景 | M2 |

**路径选择算法（宿主实现，不允许插件自选）：**

1. 编译执行图时，遍历本次请求可能经过的 Hook；
2. 若没有任何 Hook 声明 `bodyAccess: parse|transform`，选择 Raw Pass-through；
3. 否则若全部相关 Hook 的 Runtime 为 `native`，选择 Native Transform；
4. 否则若存在 `sidecar` 流处理能力，选择 Sidecar Stream；
5. 若配置显式指定了路径但该路径不满足前置条件，**启动期报错**，不做静默降级；
6. 选择结果写入请求诊断字段（`path=raw|native|sidecar`），便于排查与基准归类。

### 3.3 依赖图与执行图分离

| 维度 | 依赖图（Dependency Graph） | 执行图（Execution Graph） |
| --- | --- | --- |
| 回答的问题 | 插件能否启动 | 请求怎样运行 |
| 构建时机 | 安装/解析阶段 | 每次配置变更后编译，启动时首次编译 |
| 内容 | 能力提供与依赖、版本约束、启用状态 | 阶段 → Hook 有序列表、能力绑定、路径选择 |
| 可变性 | 随安装/启用变化 | **不可变**，整体替换 |
| 失败后果 | 启动失败并给出可定位原因 | 保留旧图继续服务，新图不生效 |
| 请求关系 | 无 | 每个进行中的请求固定使用启动时对应的图版本（理念 P08） |

**执行图编译五步：**

1. **收集**：配置 + 已解析插件清单 + 能力绑定；
2. **静态校验**：Schema 校验、能力闭合（所需能力都有提供者）、权限闭合（所需权限已被授予）、无环；
3. **编排**：按七阶段分组 Hook，同阶段内按插件声明的稳定顺序排序（禁止数字优先级隐式排序）；
4. **发布**：生成新图版本号，原子替换引用，旧图按引用计数延迟回收；
5. **记录**：图内容摘要与版本写入审计日志，供排障与回滚。

### 3.4 请求生命周期与阶段

| 阶段 | 职责 | 允许的操作 | 禁止的操作 | 可阻断 | 进入流式后可用 |
| --- | --- | --- | --- | --- | --- |
| Ingress | 解析请求、生成请求 ID、基础校验 | 读请求头/方法/路径、拒绝 | 读请求体、访问上游 | 是 | 否 |
| Identity | 身份认证与主体解析 | 凭证校验、令牌解析、短 RPC | 缓存超大响应、写账本 | 是 | 否 |
| Planning | 路由、上游/模型选择、能力绑定 | 选择目标、改写目标、选择账号 | 发起上游请求 | 是 | 否 |
| Admission | 配额、限流、准入决策 | 预占额度、排队、拒绝 | 修改响应体 | 是 | 否 |
| Execution | 发起上游调用、注入请求头 | 重试决策（受 7.2 规则约束） | 向已开始输出的响应插入内容 | 是 | 否 |
| Streaming | 分块读取、可选变换、回写客户端 | 解析、变换（须声明）、计量、背压 | 阻塞式跨进程 RPC、整包缓冲 | 仅以关闭流方式 | 是 |
| Finalize | 结算、日志、指标、清理 | 异步写入、上报 | 失败影响已发送的响应 | 否 | 是（收尾） |

阶段名称为**公共契约**，插件 Manifest 与 Hook 声明必须使用这些名称；新增阶段属于破坏性变更（6.9）。

### 3.5 关键不变量

以下约束在实现与评审中不可违反，测试需为每条提供至少一个用例：

| 编号 | 不变量 | 验证方式 |
| --- | --- | --- |
| I1 | 请求一旦开始，使用固定的执行图版本 | 热切换测试：切换期间在途请求行为不变 |
| I2 | 未声明需要解析时，响应体按字节流透传，不整包缓冲 | 大响应体 RSS 与内存峰值测试 |
| I3 | 已向客户端输出任意字节后，默认禁止跨上游重试 | 故障注入：上游中途断开，断言不重试 |
| I4 | 财务事实先持久化再对外确认，不依赖可丢事件 | 断电/崩溃恢复测试（M4） |
| I5 | 插件只能通过 Host API 访问宿主能力，不得直接引入内核内部模块 | 依赖检查（10.1）+ 代码评审 |
| I6 | 内核不出现 AI、账单、支付等业务概念 | 关键词与依赖审查 |
| I7 | 流式路径有界缓冲，背压端到端传导 | 慢消费者压测：内存增长有上界 |
| I8 | 契约变更必须版本化并附兼容测试；破坏性变更需迁移方案 | 契约破坏性检查作业 |
| I9 | 默认安装不强制任何外部服务 | 干净环境安装测试 |
| I10 | 对外性能声明必须附同环境基准数据 | 发布检查清单（10.6） |

### 3.6 部署形态演进

```text
M0–M4   单进程（Kernel + Engine + Native 插件 + Process 插件子进程）
M2      单节点多进程（新增 Sidecar 流处理进程；仍无外部服务依赖）
M5      多节点（配置分发、签名、Registry；额度与租约需原子性）
```

演进原则：**部署边界由实际压力与可靠性要求决定，不由仓库目录决定**（理念 P03）。任何“为了模块化而增加网络跳点”的设计在评审中默认否决，除非有基准或故障隔离需求支撑。
