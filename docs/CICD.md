# 构建与发布

四仓的边界保持独立：Spec 验证契约及兼容性；Go SDK 执行格式、静态检查和 race 测试；主仓运行完整 Linux 集成；官方插件通过主仓的可复用流程验证插件自身的提交。

`ci/companions.json` 固定 Spec、Go SDK 和官方插件的完整提交 ID。先推送依赖仓库，再更新主仓锁文件。集成时不跟随其他仓库的 `main`，开发依赖使用锁文件安装，发布包使用精确版本与 SHA-256。GitHub Actions 同样固定到完整提交 ID。

主仓 PR、main 推送及手动触发运行类型、格式、契约、插件、Go、公共包边界、性能基线、Docker 初始化/持久化，以及加密备份和独立恢复测试。Python 固定 3.13.5，避免 Ubuntu 默认 Python 低于备份工具要求。测试只使用临时数据，不发送外部邮件、支付或付费模型请求。

网关与官方插件测试使用 Bun 1.4.3 执行，构建工具仍固定 Node.js 24.22.0 和 pnpm 10.20.0。Docker 验收同时检查进程的实际 Bun 版本，系统状态与性能回执显示真实运行时。

推送 `v主版本.次版本.修订版本[-预发布]` 标签触发镜像交付。完整验证成功后导出实际通过测试的镜像，再由独立、具有 packages 写权限的任务发布至 `ghcr.io/moeclub-open/pluhub`，同时写入版本标签与 `sha-<提交ID>` 标签；不会在发布任务重新构建镜像。发布的 RepoDigest 和测试回执保存在 Actions Artifacts。

```sh
git tag v0.1.0-alpha.13
git push origin v0.1.0-alpha.13
```

生产部署应固定镜像 digest，在维护锁下停机备份，恢复验证通过后再切换。当前源代码推送不会自动停止 SLC，也不会将本机 SSH 凭据上传到 GitHub；SLC 的维护发布及每日备份使用部署主机工具。定时窗口与恢复命令见 [Docker 部署](DOCKER.md)。镜像发布与线上部署的结果应分别核实。
